# Overview

This gym is built from "Fast Solvers for Discrete Diffusion Models: Theory and
Applications of High-Order Algorithms" (arXiv 2502.00234).  The task is
inference for discrete diffusion models: simulating the reverse CTMC on a
multi-site categorical space well within a small budget of intensity
evaluations.  The analytic setting extends the paper's exact-score toy model
(15 states, uniform-rate noise, `T = 12`) from one site to 48 sites, the
regime where the number of evaluations is smaller than the number of sites,
so that exact simulation and site-by-site Markov chain sampling are not
viable and samplers must update all sites in parallel.

The reference is the paper's sampler at the paper's settings, with the paper's
first-order baseline and second two-stage scheme as comparison methods.  See
`briefing/problem.md` for the solver interface and `briefing/evaluation.md`
for the measurement.

---

# Problem Definition

The task is to simulate the reverse continuous-time Markov chain (CTMC) of a
discrete diffusion model and return samples whose distribution is as close as
possible to the data distribution, under a fixed budget of intensity (score)
evaluations.

## Setting

- State space `X = [S]^d` with `S = 15` states per site and `d = 48` sites.
- Forward process: every site is noised independently by the uniform-rate CTMC
  `Q = E / S - I` (the analytic model of the paper's toy experiment), run for
  horizon `T = 12`.  At time `T` the distribution is uniform up to a
  truncation error of order `e^{-T}`.
- Reverse process: the time-reversed CTMC from `p_T` (start from uniform
  samples) back to the data distribution `p_0`.  Its jump intensities are
  exact: there is no learned score, so all error comes from how the reverse
  process is simulated.
- Data distributions are synthetic multi-site distributions with several
  separated modes of unequal weight and unequal spread.  They are generated by
  the evaluators; the held-out ones are never visible.

## What a solver receives

A solver is a Python callable `solve(problem) -> np.ndarray` returning an
integer array of shape `(problem.num_samples, problem.num_sites)` with values
in `[0, num_states)`.  The `problem` object has:

| attribute | meaning |
|---|---|
| `num_samples`, `num_sites`, `num_states`, `horizon` | sizes and `T` |
| `nfe_budget` | number of intensity evaluations allowed per sample |
| `initial_states` | `(num_samples, num_sites)` uniform starting states (shared by every method) |
| `rng` | a seeded `numpy.random.Generator` (shared seed for every method) |
| `rates(states, s)` | exact reverse-process jump intensities |
| `nfe_used` | evaluations charged so far |

`rates(states, s)` takes an `(m, d)` integer array and a reverse time `s` in
`[0, T]` (a scalar, or one time per row) and returns an `(m, d, S)` array whose
entry `[j, i, y]` is the intensity of the single-site jump that sets site `i`
of row `j` to `y` (zero for the current value).  Reverse time `s` corresponds
to forward time `T - s`; `s = T` is the data end.  A request of `m` rows costs
`ceil(m / num_samples)` evaluations; requests are limited to `4 * num_samples`
rows.  Exceeding `nfe_budget`, asking for times outside `[0, T]`, invalid
states, exceptions, a time limit of 30 minutes per run, or returning samples of
the wrong shape or range all count as a failed run.

## Registering a solver

Any module under `method/` or `baseline/` that defines a top-level dict
`SOLVERS = {"name": callable, ...}` is discovered by the evaluators; every
registered name is scored as a separate method.  Solvers run in a separate
process and reach the instance only through `rates()`.  A registry that
cannot be imported, is empty, or whose solver fails on any instance or budget
receives the worst value of every scored metric.

Use `bash scripts/evaluate_train.sh` (optionally `--only NAME ...`) to score
registered solvers on the public train instances; it writes
`scoring/scores_train.json`.

# Method

The paper introduces high-order Poisson tau-leaping solvers for discrete
diffusion inference.  The baseline tau-leaping method (`baseline/tau_leaping.py`)
samples independent Poisson counts for each possible single-site jump using
the intensity at the start of each step, over an arithmetic time grid with one
evaluation per step.

`method/fast_solvers/samplers.py` implements both of the paper's two-stage
solvers (Algorithms 1 and 2) with `theta = 1/2`, an arithmetic grid on
`[0, T]` and two evaluations per step (so a budget of `B` evaluations gives
`B / 2` steps):

- **theta-RK-2**: tau-leap for `theta * Delta` to an intermediate state,
  evaluate the intensity there, then tau-leap a full step from the original
  state with the weighted intensity
  `1[mu_start > 0] * ((1 - 1/(2 theta)) mu_start + (1/(2 theta)) mu_mid)_+`.
- **theta-Trapezoidal** (the reference): the same first stage, then a second
  tau-leap from the intermediate state for `(1 - theta) * Delta` with the
  extrapolated intensity `(alpha1 mu_mid - alpha2 mu_start)_+`, where
  `alpha1 = 1 / (2 theta (1 - theta))` and
  `alpha2 = ((1 - theta)^2 + theta^2) / (2 theta (1 - theta))`.

As in the paper and the authors' released sampler, the two stages are combined
per jump increment `nu`: the intensity of jump `nu` at one state is paired with
the intensity of the same jump `nu` at the other, and jumps that would leave
`[0, S)` carry no intensity.  Updates with more than one jump along a site are
rejected.  Both solvers are registered in `SOLVERS` and run by the evaluators.

# Evaluation

The evaluators run every registered solver themselves; nothing a solver writes
to disk is read.  For each instance and each NFE budget in `{16, 32, 64, 128}`
(fewer evaluations than the 48 sites), the solver is run once on 10,000
samples with initial states and random seed shared by all methods, so methods
are compared on paired inputs.  The evaluator answers every intensity request
exactly, counts evaluations, and scores the returned samples against the exact
data distribution, which only the evaluator holds.

The train slice uses four public instances; the hidden test uses four
held-out instances drawn from the same family, with the same budgets, sample
size and metrics.

## Quantities

For a sample set `q_hat` (with add-half smoothing of empirical counts) and the
exact data distribution `p0`, KL divergences `KL(p0 || q_hat)` are computed on
three evaluator-fixed projections:

- **site marginals**: the 15-state distribution of each site, averaged over
  sites;
- **site-pair marginals**: the 225-cell joint of each of the 1128 site pairs,
  averaged over pairs;
- **mode and likelihood profile**: the joint distribution of (most likely mode
  of the sample, decile of its exact data log-likelihood), 80 cells.  It sees
  how mass is split across modes and whether whole 48-site configurations are
  typical of the data.

## Scored metrics (experiment `multisite_reverse_ctmc`)

| metric | direction | meaning |
|---|---|---|
| `log10_pair_kl_nfe16/32/64/128` | lower | log10 pair-marginal KL at each budget (geometric mean over instances) |
| `log10_profile_kl_mean` | lower | log10 profile KL, averaged over instances and budgets |
| `log10_site_kl_mean` | lower | log10 site-marginal KL, averaged over instances and budgets |
| `convergence_order` | higher | negative log-log slope of pair KL against NFE after removing the finite-sample floor |

A failed method receives `log10(20) = 1.301` for every KL metric and `-6` for
the convergence order.  The finite-sample floor at 10,000 samples is about
`0.011` for pair KL and `0.004` for profile KL.

Scores: `scripts/evaluate_train.sh` writes `scoring/scores_train.json`
(`scripts/evaluate.sh` writes the same train evaluation to
`scoring/scores.json`); the hidden `scripts/evaluate_test.sh` takes no
arguments and writes `scoring/scores_test.json`.

The hardening of this gym (iteration 11), including the shortcut audit, variant ranks and the paper-toy reproduction, is documented in `HARDENING.md`.
